## 一、项目中期总体进展情况

本项目面向地坪施工场景，致力于打造一套集地图构建、路径规划、自动研磨与实时监控于一体的智能研磨机器人协同管控系统。对照前期确立的产品需求说明书（v1.0），项目目前已按期完成核心系统架构搭建与上层业务功能模块开发，系统已打通“平板 App - 局域网 Wi-Fi - 边缘计算工控机 - 底层执行机构（雷达、移动底盘、磨盘）”的完整控制链路。

截至本报告期，设备局域网接入与协议通信、建图与地图编辑、任务区域规划、实时导航监控等核心能力均已实现闭环运行，能够支撑地图构建、区域编辑、路径规划、任务下发、状态回传和视频查看等主要作业流程。当前项目已进入算法优化、参数标定和整机联调阶段，总体进度符合预期，可为后续现场实地测试和样机验证提供支撑。

## 二、系统架构与硬件通信方案

针对地下车库、厂房地坪等典型施工现场“无公网、弱网络、环境复杂”的特点，项目设计了基于现场 Wi-Fi 的局域网可靠通信架构：

- 交互层（平板端）：平板作为现场主控入口，通过局域网与机器人建立连接，负责发起地图预览、区域编辑、路径规划、任务配置、状态查看及视频查看等操作。
- 控制层（工控机端）：工控机部署于 ROS 框架之上，运行调度节点、地图服务、路径规划适配器、视频转发服务和 SL-LinkA 协议服务，统一承接安卓平板业务请求并协调导航、底盘和磨盘执行。
- 执行层（设备端）：激光雷达通过以太网向 ROS 系统提供地图、位姿和图像数据；移动底盘和磨盘通过两路 RS-485 / Modbus RTU 接口由工控机高频写入控制寄存器，实现运动、抬降盘、启停盘和灯光等执行控制。

当前工程主目录及核心模块划分如下：

- `grinder_scheduler/`：调度核心，负责地图、任务、路径、协议和状态机。
- `grinder_chassis_driver/`：底盘驱动，负责 `/cmd_vel` 转轮速、485 通信、状态上报。
- `third_party/sl_linka/`：通信协议、SDK、安卓平板联调与调试工具。
- `third_party/path_planner/`：区域覆盖规划与两点连接规划算法实现。

## 三、核心功能模块实现及技术方案

### 3.1 设备发现与局域网连接模块

- 功能实现：  
  系统在施工现场局域网环境下提供稳定的近场连接能力。安卓平板通过 Wi-Fi 接入机器人热点后，可直接与工控机上的协议服务建立长连接，完成地图管理、任务下发和状态查看。现场使用时，操作人员在平板 WLAN 列表中选择机器人发出的 `FG_` 前缀热点后接入局域网，再通过安卓平板应用连接工控机协议服务。系统支持设备在线状态周期上报，能够在网络抖动或短时断开后恢复通信会话，降低现场操作门槛。

- 实现原理：  
  工控机侧调度程序内置 SL-LinkA 协议 TCP 服务，默认监听 `8002` 端口。服务端为每个客户端连接创建独立解析器，并通过周期线程持续回传设备状态和任务状态，形成应用层心跳保活。协议层负责对接收帧进行解码、校验、分发，并将业务请求转交给调度器具体处理函数。该模式适合无公网施工环境，能够在局域网中实现前端平板与机器人之间的稳定双向通信。

### 3.2 基于 SLAM 的建图与地图编辑模块

- 功能实现：  
  系统已实现面向地坪施工现场的建图、地图编辑与地图管理闭环能力。机器人在手动遥控状态下可边走边扫，调度程序实时接收激光雷达构建的二维栅格地图，并将地图以预览图或原始图形式回传安卓平板，用于现场即时查看建图效果。对于地下车库、厂房、走廊等空间结构差异较大的环境，系统能够持续刷新地图画面，帮助操作人员判断当前建图区域是否完整、边界是否闭合以及是否存在明显噪点。

  在地图编辑阶段，系统支持在地图上直接绘制工作区、障碍区、擦除区和裁剪区，满足“作业区定义、禁行区定义、局部噪点清除、地图范围裁切”等典型需求。工作区可用于后续的区域覆盖规划；障碍区和擦除区用于屏蔽不应进入或不应参与规划的区域；裁剪区则用于对有效施工区域进行收口，减少地图外围冗余空间对规划和显示的干扰。对于实际联调中经常出现的地图边缘虚影、孤立噪点和临时遮挡问题，这套编辑能力能够显著降低人工后处理成本。

  在地图管理方面，系统已经支持地图保存、切换、查询、删除和预览缩略图获取。每张地图在保存时会关联地图基础信息、版本号、预览图、叠层信息、区域信息及相关元数据，便于后续重复使用和问题追溯。当前工程还支持本地状态恢复，即当调度程序重启后，仍可从持久化目录中恢复已保存地图及其关联的区域编辑状态，从而保证现场作业连续性。

- 实现原理：  
  该模块的底层建图能力由激光雷达 SLAM SDK 提供，调度程序通过 ROS 话题持续订阅 `OccupancyGrid` 地图数据和 `Odometry` 位姿数据，在上层完成地图缓存、裁剪、预览和区域叠加处理。工程实现中并不是简单把雷达地图原样转发给前端，而是在调度程序内部维护“原始底图 + 编辑叠层 + 区域结构化描述”的多层数据模型：原始底图用于保存雷达给出的基础栅格结果，编辑叠层用于承载工作区、障碍区、擦除区和裁剪区等人工编辑结果，结构化区域描述则用于后续路径规划、任务下发与结果统计。

  地图服务模块在接收到区域编辑请求后，会对多边形点集、矩形区域、画刷半径和目标区域类型进行归一化处理，并将编辑结果写入内存中的地图状态对象。对于工作区等结构化区域，系统还会记录区域 ID、名称、顺序、起点、终点、规划方向等附加属性；对于擦除与障碍编辑，则会将其同步转换为覆盖层像素或区域描述，以便在地图合成和路径规划时统一使用。调度程序在生成地图预览图时，会根据请求参数决定是否叠加区域边界、缩略图信息和其他标注数据。

  持久化方面，系统采用本地状态目录管理机制保存地图及其附属信息。地图原始数据、叠层状态、区域信息、地图目录索引、缩略图和任务附属文件分别写入对应状态文件中，支持按 `map_id` 进行查询、切换和删除。删除地图时，系统会同步清理该地图关联的区域、预览状态和任务持久化信息，避免历史数据残留干扰当前使用。对于 LIVE_MAP 场景，系统还设计了单独的缓存清理机制，可在不影响已保存地图的前提下清除实时地图缓存和叠层数据。

### 3.3 任务规划与工艺配置模块

- 功能实现：  
  系统已实现面向施工工艺的可视化任务规划与参数配置能力。作业人员可在建好的地图上直接选取工作区，并进一步设置每个区域的执行遍数、路径规划方向、区域起点、区域终点以及区域执行先后关系，从而构建适应现场需求的作业任务。与单纯“整图一次性规划”的方式不同，本项目当前更强调“按区域组织作业”的思路，使得复杂场地中的分区施工、局部补磨、重复精磨和跳区执行等需求都能够在任务层进行表达。

  在任务执行逻辑上，系统已经支持多区域、多遍数和往返执行机制。对单个区域而言，可根据设置的执行遍数自动决定正向覆盖还是反向覆盖；对于多个区域组合任务，系统可根据任务中选定的区域列表与执行遍数信息，生成区域内覆盖路径和区域间连接路径，并重新拼接为供导航使用的全局执行路径。这样既保留了单区域内覆盖规划的稳定性，也兼顾了跨区域切换时的可执行性和现场可解释性。

  工艺配置方面，系统已对路径与设备关键参数开放可调，包括机器人宽度、机器人长度、路径间距、转弯半径、重叠率、膨胀半径、底盘速度、磨盘转速、磨盘启停和抬降控制等。不同施工阶段可根据工艺要求调整路径密度与设备运行参数，例如粗磨阶段可采用较大路径覆盖宽度和较高效率参数，精磨阶段则可通过增加重叠率、降低速度等方式提高作业均匀性。上述参数既可用于路径规划输入，也可用于任务执行期间的设备动作控制。

- 实现原理：  
  任务规划模块在工程实现上采用“区域内覆盖规划 + 区域间两点连接规划 + 任务级路径重组”的三层结构。第一层是单区域覆盖规划：调度程序对每个工作区单独调用覆盖规划器，根据该区域自身的边界、多边形形状、起点终点、路径方向和路径间距生成区域内部牛耕式覆盖轨迹。这里每个工作区都可以具有独立的规划方向和独立的起终点，不再依赖整张地图统一使用同一方向参数。

  第二层是区域间连接规划：当任务信息存在且涉及多个区域或多遍执行时，系统不会简单将所有工作区一起丢给一个总规划器，而是先生成每个区域自身的覆盖路径，再根据任务中设定的区域集合、执行遍数和当前遍次方向，计算上一执行段的结束点与下一执行段的起始点，并调用两点连接规划器生成过渡路径。若某区域执行奇数遍，则该区域的最终结束位置为原始终点；若执行偶数遍，则最终结束位置会回到原始起点。这个规则保证了区域之间的衔接关系可以根据任务遍数自动推导，适合后续连续导航执行。

  第三层是任务级路径重组：调度程序在拿到“区域内路径”和“区域间连接路径”之后，会按照任务结构重新拼接成完整全局路径。对于单区域多遍执行，会将正向路径与反向路径交替拼接；对于多区域任务，则会按照任务区域顺序依次插入“机器人当前位置到第一个区域起点”的连接段、“区域内部每一遍执行路径”以及“上一段结束点到下一区域起点”的连接段。最终形成的路径既可以用于预览显示，也可以直接转换为导航执行所需的全局路径点集和目标点序列。

  在参数生效链路上，调度程序会将机器人尺寸、转弯半径、膨胀半径、路径间距、路径方向等地图与规划参数传入规划适配器，将底盘速度、磨盘速度、磨盘启停和抬降控制逻辑保留在任务执行阶段使用。这样做的好处是将“路径如何生成”和“设备如何执行”分层处理：规划器只负责生成可行路径，调度器则根据路径段类型、任务状态和设备工艺要求决定何时下发导航目标、何时启停磨盘、何时抬降磨盘，从而形成更稳定的整体执行逻辑。

### 3.4 实时导航与状态监控看板模块

- 功能实现：  
  系统已实现面向施工现场作业过程的实时导航与状态监控看板。安卓平板主界面能够持续显示机器人当前坐标、航向角、当前地图、工作区轮廓、任务规划路径、任务执行状态以及底盘/磨盘相关运行状态。对作业人员而言，看板不仅用于“看见机器人在哪”，更重要的是用于判断任务是否正常推进、当前执行到哪一个区域、磨盘是否处于正确工艺状态，以及机器人是否已经发生停机、超时、偏航或通信异常等问题。

  在执行过程中，系统支持对规划路径和实际任务过程进行可视化呈现：一方面可显示当前规划得到的区域内覆盖路径和区域间连接路径，辅助确认任务生成结果是否符合预期；另一方面可在任务结束后生成带有区域结果标识的任务结果图，用于回看各区域执行遍数、完成状态和结束原因。针对多区域、多遍数作业场景，看板能够配合任务状态上报反映当前执行区域、当前进度、总路径点数以及任务完成百分比，为现场管理人员提供统一的作业观察窗口。

  同时，系统集成了视频监看能力。工控机将本地相机图像转为 RTSP 视频流，安卓平板可直接拉流查看机器人前方或侧方画面，便于观察贴边效果、磨盘姿态及现场障碍情况。对于施工现场最关心的异常处理问题，看板已经接入设备状态、底盘状态和任务状态三类信息源，可在通信异常、任务暂停、导航未推进、底盘失能或人工急停等场景下给出即时状态反馈，为人工介入提供依据。

- 实现原理：  
  该模块在工程实现上由“状态采集、状态汇总、协议上报、界面展示、异常联动”五个部分组成。首先，调度程序持续订阅地图、里程计、底盘状态、导航路径和任务执行状态等 ROS 话题，其中里程计用于计算机器人当前位置与朝向，地图用于底图显示和路径叠加，任务状态用于计算当前区域、执行进度与剩余路径。其次，调度节点在内部维护统一的运行态对象，将位姿、地图版本、任务标识、区域信息、执行点位索引和设备状态进行汇总，供协议服务和本地逻辑共用。

  在对外通信层面，SL-LinkA 协议服务以周期上报方式向安卓平板发送 `DeviceStatusReport`、`TaskStatusReport` 等消息。`DeviceStatusReport` 中包含机器人坐标、航向角、底盘使能、灯光和磨盘状态等关键运行量；`TaskStatusReport` 中则包含任务状态、执行进度、当前地图版本、当前区域面积、预计耗时、已生成路径点数等任务相关信息。安卓平板根据这些上报数据实时刷新坐标栏、任务日志区、请求返回区以及地图视图中的轨迹与状态提示，从而构成“导航执行 + 运行监控 + 结果回看”的统一交互界面。

  视频链路采用“图像订阅 + 编码封装 + 本地 RTSP 服务”的方案实现。工控机订阅本地左右相机图像，经 FFmpeg 进行实时编码后推送到 mediamtx 服务，再由安卓平板通过 RTSP 地址拉流显示。该方案的优点是与主控制协议解耦，不会因为视频带宽波动直接阻塞地图与任务控制链路，同时便于后续扩展多路相机或录制能力。

  异常联动方面，系统在调度节点和底盘驱动节点均设计了状态保护逻辑。底盘驱动负责监视串口通信超时、目标速度回读偏差、任务使能状态和安全停机条件；调度节点负责监视任务暂停、任务超时、路径段超时、导航未达点和人工停止等事件，并将相关结果写入任务结束原因与状态上报中。通过这种方式，前端看板不仅能看到“当前机器人在做什么”，还能明确知道“为什么停下”“停在了哪一步”“是主动结束还是异常中断”，从而提高现场问题定位和后续复盘效率。

### 4.1 协议服务与周期状态上报

来源：[sl_linka_adapter.py](grinder_scheduler/src/grinder_scheduler/sl_linka_adapter.py)

```python
class SlLinkAServer:
    def start(self):
        outer = self

        class RequestHandler(socketserver.BaseRequestHandler):
            def setup(self):
                self.parser = outer.SlFrameParser()
                self.running = True
                self.status_thread = threading.Thread(target=self._periodic_reports, daemon=True)
                self.status_thread.start()

            def _periodic_reports(self):
                while self.running:
                    try:
                        self._send_payload(*outer._handler.build_device_status_report())
                        self._send_payload(*outer._handler.build_task_status_report())
                    except Exception:
                        pass
                    time.sleep(1.0)

            def handle(self):
                while self.running:
                    try:
                        data = self.request.recv(4096)
                    except socket.timeout:
                        continue
                    if not data:
                        break
                    for frame in self.parser.parse(data):
                        if frame.dst_id not in (outer.pb.DEVICE_LOWER, outer.pb.DEVICE_BROADCAST):
                            continue
                        outer._dispatch_frame(self, frame)
```

说明：该段代码实现了工控机侧 TCP 协议服务、协议帧解析和设备/任务状态周期回传，是平板与机器人局域网连接的核心入口。

class _RtspPublisherWorker:
    def push_frame(self, frame):
        if not self._enabled or frame is None:
            return
        now = time.time()
        if now - self._last_frame_time < 1.0 / float(self._fps):
            return
        self._last_frame_time = now
        frame = cv2.resize(frame, (target_width, target_height), interpolation=cv2.INTER_AREA)
        with self._lock:
            self._ensure_process(frame.shape[1], frame.shape[0])
            if self._process is None:
                return
            self._process.stdin.write(frame.tobytes())
            self._process.stdin.flush()
            self._state.width = frame.shape[1]
            self._state.height = frame.shape[0]
            self._state.online = True
            self._state.last_update_utc = int(now)

    def _ensure_process(self, width, height):
        command = self._build_ffmpeg_command(width, height, encoder)
